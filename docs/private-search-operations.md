# Приватный поиск по учебным источникам

Этот инструмент запускает только оператор на VPS. Он не имеет HTTP-порта и не
вызывается из Telegram, Mini App или PWA. На VPS исходные извлечения, личные
заметки, manifest и кэш модели хранятся в ignored `.private-search/`, не в Git
и не в общем `data/` приложения. Локальные редакторские snapshots в `data/`
не передаются на VPS целиком; в search import идёт только проверенный пакет.
Вывод поиска
содержит приватные фрагменты и references; его нельзя помещать в CI logs,
публичные artifacts или ответы студентам.

## Предусловия

- Runtime и рабочий каталог: `/opt/psychology-quiz`, PostgreSQL 18.6, БД
  `psychology_atlas`, роль `psychology_app`, `DATABASE_URL` в приватном `.env`.
- Переход с закреплённого обычного образа PostgreSQL на совместимый PG18.6
  образ с pgvector 0.8.6 разрешён D-33 при точной проверке запущенной версии
  и storage, проверенных backup/restore, сверке пользовательского состояния
  и штатном lock. Один только этот документ или профиль Compose не выполняет
  переключение; до подтверждённого CD работающий образ остаётся прежним.
- Контролируемый переход создаёт schema/extension из
  `sql/private-search-bootstrap.sql`. Существующие пользовательские таблицы,
  исходные файлы и публичный content при этом не должны изменяться.
- Только пересмотренные извлечения кладутся в `.private-search/input/` на host.
  Каталог `.private-search/` не монтируется в пользовательские bot/API контейнеры;
  только search service видит input как `/data/search-input/`. Директория
  доступна оператору, manifest и файлы не доступны другим пользователям VPS.
  Каждый source должен совпадать с текущими `modified_time` и SHA-256 в
  `content/source-corpus.json` либо в явно переданном приватном дополнении;
  личная заметка имеет собственный точный SHA-256.

Manifest `.private-search/input/manifest.json` имеет `schema_version: 1`, массив
`sources` с `source_id`, `modified_time`, `snapshot_sha256`, `text_path` и
необязательный массив `notes` с `note_id`, `modified_time`,
`snapshot_sha256`, `text_path`. `text_path` относителен к `search-input`,
указывает на обычный UTF-8 файл. Для заметки `note_id` — локальный стабильный
идентификатор без Drive ID. Если `sources` не пуст, manifest также содержит
`processing_path` — относительный путь в `search-input` к приватному JSON
завершённых source reviews. Для каждого источника запись должна иметь
`review_state: processed`, ту же редакцию и SHA-256, а также reviewer,
review_note и reviewed_at. Одна запись в публичном source registry с
адресной проверкой фрагментов не разрешает индексацию всего текста. Без
доступных проверенных файлов rebuild отклоняется; новый/спорный Drive-файл
сам по себе не индексируется.

Для проверенного источника, ID которого остаётся вне Git, manifest может
содержать `private_registry_path` — имя JSON непосредственно в закрытом
`search-input`. Его `schema_version`, `corpus_root_id` и `sources` соответствуют
приватному дополнению inventory registry; совпадение с публичным source ID
останавливает загрузку. Пакет переноса включает этот файл по явной ссылке,
без ссылки файл считается неразрешённым. Registry сам по себе не разрешает
индексацию: точный `processing_path`, search ranges, revision и SHA-256
проверяются теми же gates. Приватный registry и Drive ID не попадают в Git,
CI artifact, публичный API или bot/PWA mounts.

Для каждого индексируемого источника приватная запись `processed` отдельно
содержит `search_ranges`: непересекающиеся отсортированные пары `[start, end]`
в символах точного декодированного UTF-8 текста (конец не включён),
`search_review_note` с основанием отбора, `search_reviewer` и
`search_reviewed_at`. Эти поля создаёт
`scripts/source_search_review.py` в новом ignored processing snapshot после
сверки текущей metadata revision и SHA извлечённого текста. Команда принимает
`--current`, `--prior`, `--source-id`, `--content`, повторяемые
`--range start:end`, `--reviewer`, `--note` и `--output` из `data/`. Путь к source
extract должен вести к файлу прямо в `data/`; затем выбранный snapshot
помещается в закрытый search-input как `processing_path`. Диапазоны должны
быть содержательно проверены редактором именно для индексации;
обычный `processed` или список кандидатов из поиска по словам этого не
подтверждает. Индексируются только эти диапазоны; locator в результате
указывает координаты исходного извлечения. Для полного текста нужен явный
диапазон `[0, длина текста]` после его полной проверки. При изменении SHA
или редакции источника прежний review не принимается.

## Переход действующей PostgreSQL на образ с pgvector

Первую поставку после изменения pinned image выполняет штатный CD под
`/tmp/psychology-quiz-deploy.lock` на точной проверенной merge revision. До
остановки приложения он проверяет текущий контейнер (образ, PG18.6,
checksums, сеть, bind mount и cluster), загружает закреплённый candidate
image и сверяет его PostgreSQL 18.6, UID 999 и наличие extension-файла.
До загрузки образа и повторно перед остановкой writers процедура проверяет
свободное место: минимум 1 GiB или тройной текущий размер БД (что больше)
для сосуществования работающего кластера, dump и изолированного restore.
Затем он останавливает оба writer-сервиса, создаёт native dump и проверяет
изолированное восстановление с совпадением личного состояния. Только после
этого Compose пересоздаёт PostgreSQL service на том же volume. Переход
сверяет прежний cluster ID и manifest пользовательских данных, создаёт
`private_search` schema и `vector 0.8.6` явной SQL-транзакцией, повторно сверяет
данные и сохраняет приватную фазу в `.postgres/pgvector-upgrade.json`.
Следующие поставки требуют завершённую запись перехода и extension.

После установки pgvector штатный native backup сохраняет пользовательскую
схему `public` и large objects, но исключает `private_search` и extension
`vector`: индекс и его таблицы пересоздаются из проверенного приватного input.
Перед dump процедура останавливается при неизвестной несистемной схеме либо
при `private_search` без ожидаемого extension. Изолированное восстановление
проверяет пользовательские rows/sequences под ролью приложения; одноразовый
CI-контур дополнительно восстанавливает dump после установки pgvector и
проверяет сохранение пользовательской записи. Отсутствие private index в
recovery DB ожидаемо; после восстановления реального окружения оператор
должен повторно выполнить проверенный index rebuild, не возвращая старые
непроверенные extracts автоматически.

При остановке после начала переключения приложение не перезапускается
автоматически. Сохранить `.postgres/state.json`, `pgvector-upgrade.json` и
recovery record; проверить фактический образ, кластер, здоровье БД и причину
остановки по ограниченному фрагменту логов. `image-state` показывает
`previous`, `resume` или `current` для точной revision; `resume` означает,
что `upgrade-vector-image` может продолжить по уже проверенному backup только
после сверки состояния. Не удалять volume, не выполнять `compose down` и не
восстанавливать dump поверх production без отдельного recovery-решения.
Неподтверждённое состояние или расхождение manifest блокирует CD и требует
предметного восстановления либо forward-fix. CI проверяет на одноразовом
Compose-кластере запуск старого образа с записью, переход того же volume на
candidate image, сохранность cluster ID/записи и создание расширения; это не
доказательство состояния VPS.

## Операторские команды

Команды выполняются в `/opt/psychology-quiz` после выполнения предусловий.
Профиль `search` не открывает порт и не запускает PostgreSQL автоматически.

Приватные extracts и review records не попадают в Git/CD artifact. После merge
с актуальной локальной копии `.private-search/input/` создайте закрытый пакет:

```bash
python scripts/private_search_bundle.py create \
  --manifest manifest-personality1and5-search-20260928.json \
  --cases qa-personality1and5-20260928.json \
  --output .private-search/private-search-ready-personality1and5-20260928.zip
```

Это пример локально сверенного приватного пакета на 28.09.2026;
подготовленный архив уже существует локально, поэтому команду не повторяют с тем же
output. После следующего source hold он не является последним review snapshot:
перед поставкой пересоберите пакет из актуальных review records, проверьте digest
и допуски всех включённых источников. Для новой
обработки подставьте новые имена manifest/cases и свободное имя архива. Вывод содержит
SHA-256 пакета без текста/Drive IDs. Передайте ZIP по SSH/SFTP владельца, не
через публичный GitHub artifact. На VPS только после проверки точной revision
кода установите пакет в приватный каталог; заранее задайте переменную
`BUNDLE_SHA256` равной локально полученному SHA-256:

```bash
cd /opt/psychology-quiz
chmod 600 /root/private-search-ready-personality1and5-20260928.zip
python3 scripts/private_search_bundle.py install \
  --archive /root/private-search-ready-personality1and5-20260928.zip --sha256 "$BUNDLE_SHA256"
```

Импорт сверяет digest и состав, отклоняет symlink/выход из каталога и
конфликтующие существующие файлы, сохраняет manifest последним. Повтор с
теми же байтами безопасен; другие файлы не перезаписываются. Если на VPS уже
есть `data/search-input` или `data/search-model-cache` под общим mount приложения,
импорт останавливается до записи: сначала отдельно установить происхождение и
безопасное перемещение этих файлов, не удалять их автоматически. Затем выполните
`estimate`, `probe`, `rebuild`, `status` и `qa` с именами manifest/cases из
результата импорта. В примерах ниже `manifest.json` и `qa.json` — условные
имена, замените их на имена из результата импорта. Если импорт или retrieval QA остановились, не включайте
поиск и сохраните старый индекс; приватные файлы и архив не выводите в logs.

```bash
docker compose --profile search build psych_quiz_private_search
docker compose --profile search run --rm psych_quiz_private_search \
  estimate --manifest /data/search-input/manifest.json
docker compose --profile search run --rm psych_quiz_private_search probe
docker compose --profile search run --rm psych_quiz_private_search \
  rebuild --manifest /data/search-input/manifest.json
docker compose --profile search run --rm psych_quiz_private_search status
docker compose --profile search run --rm psych_quiz_private_search \
  qa --manifest /data/search-input/manifest.json --cases /data/search-input/qa.json
docker compose --profile search run --rm psych_quiz_private_search \
  search --manifest /data/search-input/manifest.json \
  --query 'формулировка учебного вопроса' --limit 5
```

`rebuild` использует до 600 секунд на каждый SQL statement; оператор может
задать `--statement-timeout-seconds` от 30 до 3600 после оценки объёма
индекса. Это ограничение одного запроса, не обещание длительности всей
пересборки. Для `search`, `qa`, `rag` и `status` остаётся 30 секунд;
изменение timeout не обходит проверку manifest, транзакционную замену индекса
или обязательный retrieval QA.

`qa.json` — приватный файл `schema_version: 1` с 1–20 записями `cases`:
`query`, ожидаемые `source_id` и `snapshot_sha256`. После rebuild команда
проверяет первый результат фактического hybrid-поиска и точную редакцию
источника для каждого перефразированного запроса в read-only транзакции;
выводит только число успешных cases без фрагментов или Drive IDs. Ошибка
останавливает включение поиска до проверки ранжирования, данных и модели.
`search`, `qa` и будущий `rag` требуют текущий приватный manifest: перед выдачей
они сверяют разрешённые после review source fragments с точным содержимым индекса.
После нового conflict hold или изменения source revision импортируйте новый
приватный пакет и пересоберите derivative; прежний manifest не является
доказательством актуальности Drive, а несоответствующий индекс блокирует выдачу.

`rag --manifest /data/search-input/manifest.json --query 'вопрос'` подготовлен как отдельный операторский режим и по
умолчанию останавливается до обращения к БД: Compose задаёт
`PRIVATE_RAG_ENABLED=0`. Он
передаёт не более пяти коротких найденных фрагментов только в модель,
загружаемую из обычного приватного GGUF-файла в `/data/rag-model/`;
имя файла явно задаётся через `PRIVATE_RAG_GGUF`. Сетевого вызова к модели
нет. Ответ возвращается как черновик со ссылками на редакции
источников и обязательной ручной проверкой; при отсутствии фрагментов режим
воздерживается от ответа. Модель и её ресурсы ещё не утверждены по Q-05,
поэтому установка локальной зависимости, выбор модели и включение этого
режима в поставку пока не разрешены. После замеров и отдельного решения
оператор должен явно включить режим, установить локальную dependency и
подключить приватный файл модели; текущая поставка этого не делает.

`estimate` не подключается к БД и возвращает только количество sources,
chunks и нижнюю границу объёма текста/векторов. `probe` отдельно загружает
локальную embedding-модель и измеряет время первого вектора и размер кэша,
не читая приватный corpus и не подключаясь к БД. Его выполняют до решения о
ресурсной достаточности; он может скачать модель в приватный кэш. Модель
закреплена на конкретной ревизии ONNX/tokenizer в Hugging Face вместе с
версией FastEmbed; эта identity хранится в marker индекса. Изменение модели
или pooling требует явной пересборки derivative. Локальный probe на Windows
27.09.2026: около 252 МБ кэша и 30 секунд первого скачивания/вектора;
это не измерение VPS и не обещание ресурсов production.
Индекс использует короткие перекрывающиеся фрагменты из-за окна входа модели;
перед включением оператор проверяет качество поиска по перефразированным
запросам и точность возвращённых символьных диапазонов.
Оценка не включает HNSW,
полнотекстовый индекс, кэш модели и backups; по ней одной нельзя признать
ресурсы достаточными. `rebuild` заменяет производный индекс транзакционно в
отдельной `private_search` schema. `status` и `search` используют read-only
транзакцию. Результат поиска показывает точную редакцию источника и диапазон
символов; семантический матч остаётся кандидатом для сверки, а не
подтверждением истинности ответа. Код RAG не является разрешением на запуск
модели и не заменяет оценку качества/ресурсов; отдельная vector DB не включена.
При изменении поискового кода CI собирает приватный search image, проверяет
его CLI без сети и поднимает одноразовую PostgreSQL 18.6 с pgvector 0.8.6.
Затем он проверяет создание индекса, поиск, замену derivative и
сохранность отдельной учебной таблицы. Одноразовый CI не подтверждает
состояние образа или доступность ресурсов на действующем VPS.
Неразрешённый конфликт другого processing record, указывающий на источник
через `related_source_ids`, удерживает его от индексации и signed publication
даже при собственной записи `processed`; требуется отдельное содержательное
разрешение конфликта. Для image upgrade и включения RAG действуют решения и проверки из
[project-spec.md](project-spec.md).

При ошибке не повторять rebuild вслепую: сохранить прежний индекс и причину
остановки, проверить manifest, редакции и состояние DB. Восстановление
первичных источников и пользовательского прогресса этим инструментом не
выполняется.
