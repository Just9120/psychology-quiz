# Поставка банка вопросов и сохранение попыток

Canonical derivative — JSON в content/questions; [seed](../scripts/seed_questions.py) читает полный набор module directories. Это authoritative sync: approved rows обновляются, supplied non-approved IDs снимаются с выдачи, отсутствующие IDs становятся retired. Частичный вызов DB helper не снимает approval с неуказанных IDs. Вопросы и пользовательская история физически не удаляются.

При включении вопроса в попытку [attempt content](../app/attempt_content.py) сохраняет JSON v1, SHA-256 и provenance `captured` в quiz_session_questions. Текущий вопрос, варианты, оценка и feedback в API и классическом Telegram используют этот snapshot. Изменение текста, порядка/числа вариантов, верного ответа, approval или удаление JSON не меняет существующую попытку. Новые attempts используют актуальный approved банк.

Additive migration [init](../scripts/init_db.py) и bot startup заполняют отсутствующие snapshots до seed с provenance `legacy_backfill_current`. Это доступная на момент миграции редакция, а не восстановленный исторический оригинал. Оригинальные answers/score не пересчитываются. Hash проверяется при чтении, DB trigger запрещает перезапись сохранённой редакции. Transaction защищает связанное чтение question/options; повторная migration/seed не заменяет snapshot.

## Проверка происхождения и публикация

[Source registry](../content/source-corpus.json) хранит только прочитанные источники согласованного Drive corpus: file ID, путь, modified time, fingerprint snapshot, способ чтения и ограничения. `kind: bibliography` означает текст списка литературы; это не доступ к содержанию перечисленных книг. Такой источник разрешён для `bibliographic_metadata`, но не для `learning_content`. Интернет, LLM, Obsidian, старые вопросы и supplied snippets не заменяют прямую проверку corpus для нового approval. Рекурсивная metadata-инвентаризация 25.09.2026 17:36 UTC охватила root и 91 вложенную папку / 413 файлов; прочитаны 14 явно обозначенных библиографий в предыдущем срезе, не все встроенные списки внутри лекций. Новые/изменённые файлы не считаются содержательно проверенными; это ограничение сохраняется в registry.

Приватный export для [inventory report](../scripts/source_inventory_report.py) имеет `schema_version: 1`, `root_id` и `folders: {folder_id: [pages...]}`. Каждая страница содержит `page_token` (первая — `null`), `next_page_token` (`null` только на последней) и `children` с прямыми `parent_ids`; file records содержат `id`, `title`, `mime_type`, `modified_time`, `file_or_folder: file`, folder records — `id`, `title`, `parent_ids`, `file_or_folder: folder`. Все страницы каждой вложенной папки должны быть получены; обрыв cursor chain, duplicate в одной папке или неизвестный parent останавливает отчёт. `--previous` принимает такой же export, `--processed` — map file ID к `revision: [modified_time,title,mime_type]` и `review_state: pending_review | conflict | processed`. Для `processed` требуются `snapshot_kind: file_bytes | extracted_text` и `snapshot_sha256` (64 строчные hex); для `conflict` — непустой `reason`. Это подтверждение наличия зафиксированного снимка, а не содержательной правильности или approval. `--links` — список явно проверенных `{source_id,lesson_id,topic_id,format}`. `new/changed/relocated/missing` — metadata изменения и очередь проверки, не команды удаления; `processed` не даёт права публикации. Полные exports, cursors, extracted text и raw logs остаются в ignored `data/` или другом приватном operator storage, не в PR/artifacts. Сводка показывает только counts и не заменяет содержательный source review.

Режим `--reviewed` приватного [inventory report](../scripts/source_inventory_report.py) сравнивает полный metadata export с canonical source registry и curriculum: точные source revisions, ссылки занятий и количество файлов вне registry. Выводит только агрегаты; `current` подтверждает title/modified_time/corpus_path, а не содержательный review или соответствие snapshot hash исходному файлу. Файлы вне registry требуют отдельного чтения и решения; связи не назначаются автоматически. Если `--processed` и `--links` не переданы, их сводки нельзя трактовать как отсутствие уже проверенных материалов или связей.

Опция `--private-queue` требует `--reviewed` и записывает новый пофайловый JSON только непосредственно в Git-ignored `data/`: ID, пути, revision, состояние registry, подтверждённые topic IDs и статусы обработки, если передан `--processed`. Без previous/processed snapshot соответствующие поля явно unknown. Existing queue не перезаписывается. Перемещение в другую папку при той же title/modified_time даёт `relocated` и требует проверки связи с занятием; это не доказательство изменения текста. Частные очереди не включают в PR, CI artifacts или клиентские assets.

Новый файл Drive сам не публикуется. Coding/reasoning agent в разрешённом content scope читает материал, фиксирует его revision и доступный fragment/page/section, подготавливает derivative как `draft`/`review`, проверяет содержание и только затем добавляет запись в [publication reviews](../content/publication-reviews.json). Approval проходит обычный repository PR/CI/review. Политика не обращается в Drive из runtime и не вызывает LLM. Автоматическая проверка связывает records и редакции; истинность содержательного review подтверждает сама работа с источником, а не строка `reviewer`.

Ключ review — `questions:ID`, `glossary:ID` или `literature:ID`. Запись содержит `decision: approved`, `item_sha256` из `app.content_publication.fingerprint(item)`, `purpose` (`learning_content` для quiz/glossary, `bibliographic_metadata` для literature), `reviewer`, дату `reviewed_at` формата YYYY-MM-DD и непустой `sources`. Каждый source evidence содержит `source_id`, `modified_time`, `snapshot_sha256` из registry и точный `locator`. Item использует прямые `drive:FILE_ID#locator` в `source_ref`/`source_refs`; множество source IDs должно совпадать с review. Изменение любого поля item или source revision требует нового review, а не переноса прежнего approval. Fingerprint источника относится к PDF bytes или к извлечённому тексту по `snapshot_kind`, не к тексту упомянутой книги.

Legacy исключение ограничено [frozen baseline](../content/legacy-publication-baseline.json) на `dabb280`: 575 questions, 99 glossary items и 42 ранее видимых bibliography entries. Оно сохраняет работающий продукт без переутверждения первичных источников. Полный checksum baseline закреплён в [publication policy](../app/content_publication.py); добавлять туда новые items запрещено. Изменённый материал требует обычного source review для публикации. Сохранённые snapshots текущих попыток не исчезают при снятии publication с исходного item. F-007 и полный source certification прежнего банка остаются отдельной работой.

Canonical validators из [README](../README.md#быстрый-старт-и-проверки) проверяют publication ledger дополнительно к структуре JSON. Seed проверяет его до DB writes; glossary/literature loaders показывают только точный legacy либо approved derivative с валидным review. Новые `draft`, `review`, `deprecated`, `placeholder` не видны пользователю. Политика кэшируется в процессе как часть immutable release: после content/review обновления нужен штатный runtime restart через CD. Legacy literature `review` — явно ограниченное исключение, а не разрешение автоматически показывать новые review entries.

## Содержательный review учебного банка

[Learning quality ledger](../content/learning-quality-reviews.json) охватывает 575 вопросов и 99 терминов восьми дисциплин. Он фиксирует review смысла, ключа/определения, объяснения/примера, неоднозначности, повторов и источников на точном fingerprint item. Primary fragments связаны с revision/fingerprint из source registry и locator; `partial`/`disputed` сохраняют причины ограничения. Discipline summaries описывают смысловые повторы; они не дают основания автоматически удалять IDs или историю.

Ledger не является publication approval, SME certification или заявлением о прочтении всех материалов корпуса. `supported` означает соответствие указанному фрагменту, а не универсальную истинность каждого клинического/методологического обобщения. Known issues сохранены и у поддержанных источником items. Подтверждённые исправления проходят отдельный publication review; старые ответы продолжают использовать snapshots. Полная сертификация legacy и устранение всех замечаний остаются F-007/008 в [плане](delivery-plan.md).

`validate_learning_reviews.py` из canonical commands [README](../README.md#быстрый-старт-и-проверки) обнаруживает пропущенные/лишние/stale items, изменившиеся sources, неполные review aspects и скрытую неопределённость. Repository regression выполняется общей pytest suite. Добавление или изменение content/source требует нового содержательного review; обновление hash без проверки источника не закрывает замечание. Raw snapshots и исследовательские заметки хранятся вне repository.

## Каталог литературы

[Литературные записи](../content/literature/) хранят отдельно библиографические связи и группировку работ. `id` — стабильный ключ записи учебного списка и существующего `user_literature_progress`; `work_id` ссылается на canonical запись той же работы. Повторные упоминания объединяются только после review автора/названия/гранулярности; совпадение названий не доказывает одинаковое произведение или издание. `module`/`topic_id` соответствуют [registry](../content/topics.json); `source` содержит ID списка, title, locator и исходную citation. Source revision/fingerprint и review находятся в едином publication ledger. Новые literature-only topics имеют `question_file: null` и не создают пустых quiz/glossary разделов.

Проверенный срез: 14 явных списков из согласованного corpus, 130 записей, 114 работ, 12 тем. Сохранены все 42 прежних IDs. Пятнадцать physiology/VND пар и Алешина counseling/family сгруппированы после ручного сравнения; отдельные годы/цитаты/источники остаются у каждой связи. Вложенные библиографии внутри всех лекций не заявлены как полностью просмотренные. Новая книга, revision или grouping требуют обычного review; frozen legacy baseline не расширяется.

`content_access: not_verified` означает, что содержание работы не использовано как учебное знание: прочитана только библиография. Отсутствующие авторы — пустой список с явной metadata warning; неизвестные год/уровень/приоритет/время — `null`, learning outcomes не выдумываются. Спорные данные остаются в citation и `metadata_warnings`. Validators проверяют структуру, ссылки и точные publication fingerprints, а не истинность содержания недоступной книги.

PWA `GET /web/literature/catalog` группирует works, но оставляет состояние каждой association отдельно. `POST /web/literature/progress` и существующий Mini App adapter используют [общий сервис](../app/literature_service.py) и проверенный actor. Пять legacy reading statuses сохраняются до решения Q-04. Никакого автоматического слияния, переноса или удаления reading rows/private notes нет; readback не раскрывает private_note. В PWA выбор учебного списка определяет, какая отметка будет изменена. При потере подтверждения записи сначала требуется readback. Личный прогресс не попадает в browser persistent cache; автоматической синхронизации открытых вкладок нет, актуальное состояние загружается при входе в раздел или по кнопке обновления.

## Release gate

Поставка следует [действующей VPS процедуре](miniapp-deployment-qa.md#действующие-правила-и-delivery-snapshot). Для schema/seed changes класс BACKWARD_COMPATIBLE_AUTOMATED: добавить поля, не удалять существующие; на время backup/migration остановить writers. Build candidate происходит до изменения DB. SQLite backup API и isolated restore rehearsal обязательны; затем init/backfill → seed → integrity/FK и сравнение прежних user fields → snapshots/serving smoke и canonical parity → runtime start/version/health. Проверенные команды и порядок заданы [deploy.sh](../deploy.sh), [DB checks](../scripts/deployment_db.py) и [parity audit](../scripts/audit_question_bank.py).

При failed migration/post-check не продолжать поставку и не восстанавливать production автоматически. Сохранить backup/manifest, run ID и candidate SHA; сверить DB integrity/user preservation и подготовить forward-fix. Старый backend не читает snapshots, поэтому приложение не откатывается автоматически даже при совместимой additive schema. Отсутствующая/повреждённая редакция не подменяется текущим content.

Массовое обновление content — отдельный согласованный scope: content смонтирован read-only с host checkout, который обновляется до runtime restart. Размещение больших releases и проверка duration/lock window определяются до соответствующей поставки; неизменённый банк не требует искусственного content rollout.

## Unfinished sessions

После внедрения snapshots обычный seed не требует abandon активных attempts: они продолжают исходную редакцию. [abandon script](../scripts/abandon_in_progress_sessions.py) остаётся только для отдельно разрешённой операции закрытия попыток. Он не восстанавливает смысл ранее изменённой истории и не вызывается автоматически CI/CD или startup.
