# Поставка банка вопросов и сохранение попыток

Canonical derivative — JSON в content/questions; [seed](../scripts/seed_questions.py) читает полный набор module directories. Это authoritative sync: approved rows обновляются, supplied non-approved IDs снимаются с выдачи, отсутствующие IDs становятся retired. Частичный вызов DB helper не снимает approval с неуказанных IDs. Вопросы и пользовательская история физически не удаляются.

При включении вопроса в попытку [attempt content](../app/attempt_content.py) сохраняет JSON v1, SHA-256 и provenance `captured` в quiz_session_questions. Текущий вопрос, варианты, оценка и feedback в API и классическом Telegram используют этот snapshot. Изменение текста, порядка/числа вариантов, верного ответа, approval или удаление JSON не меняет существующую попытку. Новые attempts используют актуальный approved банк.

Additive migration [init](../scripts/init_db.py) и bot startup заполняют отсутствующие snapshots до seed с provenance `legacy_backfill_current`. Это доступная на момент миграции редакция, а не восстановленный исторический оригинал. Оригинальные answers/score не пересчитываются. Hash проверяется при чтении, DB trigger запрещает перезапись сохранённой редакции. Transaction защищает связанное чтение question/options; повторная migration/seed не заменяет snapshot.

## Проверка происхождения и публикация

В приватной очереди `cross_folder_title_review_candidates` показывает разные файлы с одинаковым нормализованным названием в разных папках. Это только сигнал для проверки дублирования или принадлежности к занятиям; общее название само по себе не создаёт связь между материалами.

[Source registry](../content/source-corpus.json) хранит только прочитанные источники согласованного Drive corpus: file ID, путь, modified time, fingerprint snapshot, способ чтения и ограничения. `kind: bibliography` означает текст списка литературы; это не доступ к содержанию перечисленных книг. Такой источник разрешён для `bibliographic_metadata`, но не для `learning_content`. Интернет, LLM, Obsidian, старые вопросы и supplied snippets не заменяют прямую проверку corpus для нового approval. Рекурсивная metadata-инвентаризация 25.09.2026 17:36 UTC охватила root и 91 вложенную папку / 413 файлов; прочитаны 14 явно обозначенных библиографий в предыдущем срезе, не все встроенные списки внутри лекций. Новые/изменённые файлы не считаются содержательно проверенными; это ограничение сохраняется в registry.

Приватный export для [inventory report](../scripts/source_inventory_report.py) имеет `schema_version: 1`, `root_id` и `folders: {folder_id: [pages...]}`. Каждая страница содержит `page_token` (первая — `null`), `next_page_token` (`null` только на последней) и `children` с прямыми `parent_ids`; file records содержат `id`, `title`, `mime_type`, `modified_time`, `file_or_folder: file`, folder records — `id`, `title`, `parent_ids`, `file_or_folder: folder`. Все страницы каждой вложенной папки должны быть получены; обрыв cursor chain, duplicate в одной папке или неизвестный parent останавливает отчёт. `--previous` принимает такой же export, `--processed` — map file ID к `revision: [modified_time,title,mime_type]` и `review_state: pending_review | conflict | processed`. Для `processed` требуются `snapshot_kind: file_bytes | extracted_text` и `snapshot_sha256` (64 строчные hex); для `conflict` — непустой `reason`. Это подтверждение наличия зафиксированного снимка, а не содержательной правильности или approval. `--links` — приватный список явно проверенных `{source_id,lesson_id,topic_id,format,revision,corpus_path,reviewer,reviewed_at,review_note}`; `revision` равна текущим `[modified_time,title,mime_type]`, `corpus_path` — один из текущих путей, `reviewed_at` содержит timezone. Устаревшая revision/path останавливает отчёт до повторной проверки связи. `new/changed/relocated/missing` — metadata изменения и очередь проверки, не команды удаления; `processed` и link не дают права публикации. Полные exports, cursors, extracted text и raw logs остаются в ignored `data/` или другом приватном operator storage, не в PR/artifacts. Сводка показывает только counts и не заменяет содержательный source review.

У `processed` дополнительно обязательны непустые `reviewer`/`review_note` и `reviewed_at` с timezone. Пустая запись не подтверждает ручную проверку источника. При `--reviewed --private-queue --links` файл очереди получает `linked_lesson_ids` по каждому источнику и `link_state` для совпадающих по имени форматов: `linked` только при общем проверенном lesson ID у всех файлов группы, иначе `candidate`. Без `--links` эти признаки не доказывают отсутствие ранее проверенных связей.

Режим `--reviewed` приватного [inventory report](../scripts/source_inventory_report.py) сравнивает полный metadata export с canonical source registry и curriculum: точные source revisions, ссылки занятий и количество файлов вне registry. Выводит только агрегаты; `current` подтверждает title/modified_time/corpus_path, а не содержательный review или соответствие snapshot hash исходному файлу. Файлы вне registry требуют отдельного чтения и решения; связи не назначаются автоматически. Если `--processed` и `--links` не переданы, их сводки нельзя трактовать как отсутствие уже проверенных материалов или связей.

Новые проверенные источники, чьи Drive ID нельзя вносить в публичный registry, можно учитывать только в приватном отчёте: `--reviewed --private-registry data/<private-registry>.json`. Файл находится непосредственно в ignored `data/` и имеет `schema_version: 1`, тот же `corpus_root_id` и массив `sources` в формате source registry. CLI добавляет эти записи к публичным только для сверки inventory и приватной очереди; совпадающие ID, другая corpus root, tracked path и symlink отклоняются. Stdout содержит только агрегаты. Это не делает источник публичным, не меняет `content/source-corpus.json`, не выдаёт разрешение на подпись/публикацию и не заменяет проверку текста. Для нового опубликованного производного материала нужен отдельный приватный publication review с точной редакцией и разрешённой процедурой подписи.

Перед новым approval при свежем полном export запусти из корня `python scripts/source_inventory_report.py --current data/<private-export>.json --reviewed --require-current-reviewed`. Ненулевая ошибка `reviewed_source_revision_not_current` означает изменённый, перемещённый или отсутствующий учтённый источник: останови approval до повторной сверки. Успех подтверждает только совпадение metadata с переданным снимком, не неизменность байтов, полноту содержательного review или состояние Drive после экспорта. Неучтённые файлы остаются в приватной очереди и не получают approval автоматически.

Приватная очередь `--private-queue` дополнительно связывает каждый tracked источник с approved derivatives из `content/publication-reviews.json`. `linked_derivative_ids` показывает все связи, а `derivative_ids_requiring_review` — те, для которых live файл изменился/переместился/исчез либо revision/hash в publication review не совпадают с source registry. `derivative_review_required` — признак непустого второго списка. Очередь не изменяет публикацию автоматически и не попадает в агрегированный stdout. Неизвестный source ID в review останавливает формирование очереди.

Для source-free подписанных материалов добавьте `--private-publication-dossiers data/<private-dossiers>.json` вместе с `--private-queue`. Документ версии 1 содержит массив `dossiers` с исходными приватными досье подписи. Отчёт восстанавливает source edges только при действительной Ed25519 подписи текущего public item и точном совпадении SHA досье с certificate; старый/изменённый item, досье, дубликат или недействительная подпись отклоняются. Legacy publication acceptance не заменяет проверку certificate. Личные данные и source states не изменяются, приватные refs остаются только в очереди; stdout дополнительно содержит число `signed_private_derivatives`. Этот механизм восстанавливает provenance, не одобряет источник целиком и не снимает его holds.

Опция `--private-queue` требует `--reviewed` и записывает новый пофайловый JSON только непосредственно в Git-ignored `data/`: ID, пути, revision, состояние registry, подтверждённые topic IDs и статусы обработки, если передан `--processed`. Без previous/processed snapshot соответствующие поля явно unknown. Existing queue не перезаписывается. Перемещение в другую папку при той же title/modified_time даёт `relocated` и требует проверки связи с занятием; это не доказательство изменения текста. Частные очереди не включают в PR, CI artifacts или клиентские assets.

[Source capture](../scripts/source_capture.py) принимает полный `--current` inventory export, `--source-id`, локальный приватный `--content`, `--snapshot-kind file_bytes|extracted_text`, необязательный `--prior` processing map и новый `--output` непосредственно в ignored `data/`. Для `extracted_text` необязательный `--extraction-profile` фиксирует стабильный идентификатор метода извлечения, который оператор должен уметь воспроизвести; он не доказывает неизменность источника. Команда читает непустой файл, считает SHA-256 фактических байтов и сохраняет ревизию из inventory только как `pending_review`; для `extracted_text` дополнительно требует UTF-8. Предыдущий processing JSON не перезаписывается, другие records сохраняются; уже `processed` запись той же редакции не понижается, новая редакция создаёт pending review. При существующем `conflict_review` той же редакции обычный захват остановится. Явный `--capture-conflict-evidence` допускает только добавление kind/SHA точного файла к этой conflict-записи, не меняя статус, причину, ссылки и запрет публикации; повтор и несовпавший digest останавливаются. В stdout нет source ID, текста и digest. Operator должен подтвердить, что переданный контент действительно соответствует указанной Drive revision: один metadata export и локальный файл сами по себе этого не доказывают. `processed` и publication approval требуют отдельного содержательного review.

Если connector передаёт извлечённый текст через API, [capture_private_text.py](../scripts/capture_private_text.py) принимает его UTF-8 bytes как одну base64-строку через stdin либо `--encoded-file` непосредственно из ignored `data/`. Передай независимо зарегистрированный `--expected-sha256` и новый `--output data/<capture>.txt`: несовпадение digest, повторная запись и вывод за приватную директорию блокируются до записи; текст не печатается. Это только доставка extract к `source_capture.py`, а не содержательная проверка или разрешение на публикацию. Временный base64-файл после подтверждённого exact capture удали.

При захвате изменённой редакции последнее завершённое review сохраняется в `previous_processed_review`; повторный захват pending-редакции сохраняет ту же цепочку. История нужна для сравнения и не даёт новой редакции статус `processed` или разрешение публикации. Цепочка проверяется валидатором, повреждённый record останавливает обработку.

Для отдельного проверенного фрагмента [sign_private_publication.py](../scripts/sign_private_publication.py) поддерживает приватное `scoped_claim_review` версии 2. [Проверка фрагмента](../scripts/scoped_fragment_review.py) привязывает решение к одному производному item, его полному fingerprint, текущей редакции источника, SHA фактического UTF-8 extract, точным `characters:start:end` ranges и SHA выбранных фрагментов. Fingerprint всей processing-записи связывает доказательство со всеми известными удержаниями; пересечение с любым удержанным диапазоном, issue без диапазона, неразрешённый hold прежней редакции и related-source conflict блокируют подпись. Новое решение не меняет processing state источника, не одобряет его целиком и не отменяет source-kind, quality и publication gates. Для вопросов/глоссария требуется явное одобрение quality review; для литературы допускается только отдельное решение `bibliographic_metadata`, которое не подтверждает научные утверждения материала. Прежние три узких исключения остаются на своём прежнем пути и не могут использовать версию 2. Досье, ranges и source IDs остаются приватными; разрешение публикации и проверка текущего inventory сохраняются.

Для нового источника, классифицированного только в приватном operator registry, signer принимает необязательный `--private-registry data/<reviewed-registry>.json`. Файл проходит ту же проверку ignored storage, владельца и corpus root, что и inventory report; замена публичной записи или повтор ID запрещены. Классификация должна совпадать с текущими title/revision/kind и processing SHA, иметь точный receipt на фактический extract и согласованного reviewer/date. Этот путь допускает только fragment review v2; classification не переводит источник в processed и не даёт publication approval. Подмена extract, пустой/неверный диапазон, удержанный фрагмент или отсутствие отдельного publication/quality review блокируют подпись. Private registry и его receipts не входят в public assets или certificates.

Если независимые приватные review snapshots расходятся, используйте [fail-closed merge](../scripts/source_processing_merge.py) с полным `--current` inventory, более поздней `--base`, дополнительной `--supplement` и новым ignored `--output`. Обе карты сверяются с текущим inventory. Автоматически объединяются только одинаковые записи, непересекающиеся поля `search_*` одной завершённой review и более поздний conflict hold поверх точно того же pending capture; иные различия останавливают merge. После readback пересоздайте очередь и приватный search bundle из объединённой карты. Старые snapshots остаются для provenance, но не являются актуальным операторским input.

[Source finalize](../scripts/source_finalize.py) после ручного review принимает тот же приватный `--content` вместе с `--current`, `--prior`, `--source-id`, непустыми `--reviewer` и `--review-note`, а также новым `--output` в ignored `data/`. Укажите проверенный `--source-kind learning_material|bibliography` для нового источника: тип сохраняется с reviewer, note и timestamp, а приватная публикация сверяет его с досье; для уже учтённого источника она дополнительно сверяет тип, редакцию и digest с canonical source registry. Старые processing records без типа читаются, но новый неучтённый источник без него нельзя подписать. Finalize повторно сверяет SHA-256 и текущую Drive metadata revision с captured `pending_review`, затем записывает `processed` с атрибуцией решения. Прямой `conflict_review` не завершается; если новая ревизия захвачена с `conflict_hold`, дополнительно требуется непустой `--conflict-resolution-note` с результатом сравнения противоречащих источников. До такого решения private queue удерживает derivatives обоих источников. Изменённые байты и попытка перезаписи output останавливают операцию. Это запись факта review в приватной очереди, не approval производного вопроса или утверждение достоверности содержания; соответствие локального файла оригиналу Drive редактор подтверждает отдельно.

Новый файл Drive сам не публикуется. Coding/reasoning agent в разрешённом content scope читает материал, фиксирует его revision и доступный fragment/page/section, подготавливает derivative как `draft`/`review` и проверяет содержание. Для нового вопроса или термина provenance и решение остаются в приватном досье и подписывается только публичная проекция; прямой [publication review](../content/publication-reviews.json) относится к существующему разрешённому пути других производных материалов. Approval проходит обычный repository PR/CI/review. Политика не обращается в Drive из runtime и не вызывает LLM. Автоматическая проверка связывает records и редакции; истинность содержательного review подтверждает сама работа с источником, а не строка `reviewer`.

Ключ review — `questions:ID`, `glossary:ID` или `literature:ID`. Запись содержит `decision: approved`, `item_sha256` из `app.content_publication.fingerprint(item)`, `purpose` (`learning_content` для quiz/glossary, `bibliographic_metadata` для literature), `reviewer`, дату `reviewed_at` формата YYYY-MM-DD и непустой `sources`. Каждый source evidence содержит `source_id`, `modified_time`, `snapshot_sha256` из registry и точный `locator`. Новый вопрос и термин используют приватный путь с сертификатом ниже: их публичная редакция не содержит Drive ID/locator. Прямые `source_ref` старых редакций остаются только в ограниченном историческом пути, предусмотренном policy; он не разрешает новые публичные вопросы с такими ссылками. Для нового вопроса или термина также нужен независимый review качества с тем же fingerprint и набором источников, `supported`/`consistent` без открытых issues и проверенными аспектами содержания. Локатор `extracted text …: 0:<end>` требует уточнения фрагмента перед новым approval и отклоняется как в publication, так и в quality evidence; это не пересматривает frozen legacy. Частичный или устаревший quality review не разрешает публикацию. Изменение любого поля item или source revision требует нового review, а не переноса прежнего approval. Fingerprint источника относится к PDF bytes или к извлечённому тексту по `snapshot_kind`, не к тексту упомянутой книги.

Для терминов глоссария и других материалов, чьи Drive references должны оставаться приватными, действует второй путь с теми же содержательными gates: публичный item не содержит `source_ref`/`source_refs` и ID исходного файла. Приватное JSON-досье в ignored `data/` содержит `schema_version: 1`, `kind`, `item_id`, случайный приватный `nonce` (64 hex), прямой `source_ref` либо `source_refs`, полные проверенные `sources`, `publication_review` и для учебного материала `quality_review`. Их fingerprints относятся к item **с** приватной ссылкой. [Signer](../scripts/sign_private_publication.py) требует `--inventory` со свежей полной приватной выгрузкой и `--processed` с завершённой проверкой каждого источника: file identity, revision и extract digest должны совпадать с досье. Только для уже опубликованного термина «Дофамин» допускается узкое подтверждение фрагментов источника под `conflict_review`: `scoped_claim_review` привязывает точный item fingerprint, source revision, полный конфликтный record, непересекающиеся диапазоны символов и digest фрагментов из приватного extract; оно не снимает удержание остальной лекции и не разрешает другие derivatives. Затем signer запускает прежнюю [publication policy](../app/content_publication.py) на полном item и сверяет locator и quality, прежде чем подписать точный fingerprint публичной проекции. Его output остаётся новым файлом в ignored `data/` до явного переноса одной записи в [public certificates](../content/publication-certificates.json). Публичный certificate содержит только fingerprint item, digest приватного досье, ID публичного Ed25519-ключа и подпись. CI/runtime проверяют подпись по `content/publication-review-public-key.hex` и отклоняют изменения item, подмену сертификата и смешение приватного и публичного путей. Signer читает существующий PEM только из пользовательского `~/.codex/secrets/psychology-quiz/`, вне checkout; на POSIX требует права владельца `0600`. Это ключ авторизации новых публикаций, не ключ GitHub/CD: закрытая часть не нужна на VPS и может повторно использоваться для будущих проверенных items, пока открытая часть закреплена в репозитории. Локальный ключ создан по явному разрешению владельца 27.09.2026; закрытый ключ и полное досье никогда не входят в Git, assets или CI. Два предложенных вопроса владелец оставил черновиками. Сертификат удостоверяет review на момент подписания, а не текущесть Drive или истинность непроверенного утверждения; обнаруженная позднее правка источника требует снятия approval до нового приватного review и подписи.

Перед подписью signer сверяет видимый текст нового item со всеми file IDs полного приватного inventory, в том числе не входящими в его досье. Голый ID другого источника в вопросе или пояснении блокирует сертификат так же, как прямая Drive-ссылка; совпадение редакции и content review этот запрет не снимают.

Legacy исключение ограничено [frozen baseline](../content/legacy-publication-baseline.json) на `dabb280`: 575 questions, 99 glossary items и 42 ранее видимых bibliography entries. Оно сохраняет работающий продукт без переутверждения первичных источников. Полный checksum baseline закреплён в [publication policy](../app/content_publication.py); добавлять туда новые items запрещено. Изменённый материал требует обычного source review для публикации. Сохранённые snapshots текущих попыток не исчезают при снятии publication с исходного item. F-007 и полный source certification прежнего банка остаются отдельной работой.

Canonical validators из [README](../README.md#быстрый-старт-и-проверки) проверяют publication ledger дополнительно к структуре JSON. Seed проверяет его до DB writes; glossary/literature loaders показывают только точный legacy либо approved derivative с валидным review. Новые `draft`, `review`, `deprecated`, `placeholder` не видны пользователю. Политика кэшируется в процессе как часть immutable release: после content/review обновления нужен штатный runtime restart через CD. Legacy literature `review` — явно ограниченное исключение, а не разрешение автоматически показывать новые review entries.

Изменение `learning-quality-reviews.json` может снять approval нового учебного derivative. Поэтому штатный CD классифицирует его вместе с правилами publication/evidence как stateful content sync: до `init_db.py` и `seed_questions.py` выполняется проверенный backup, после — сохранность user state и serving parity. Простого перезапуска runtime для такой редакции недостаточно.

Для ещё не опубликованного занятия используй `--private-topics data/<private-topics>.json` вместе с `--private-registry` и `--reviewed`. Приватный файл непосредственно в ignored `data/` содержит `schema_version: 1`, тот же `corpus_root_id` и `topics` как map стабильного `t_<12 hex>` ID к `{title, discipline_id, source:{source_id, modified_time, snapshot_sha256}}`. Source ID обязан быть в переданном приватном registry, topic ID не должен повторять публичный. Дисциплина может быть в canonical curriculum; для ещё не опубликованной дисциплины добавь в тот же приватный файл `disciplines` как map нового латинского ID к `{title}`. Публичную дисциплину нельзя заменить приватной. `--links` может привязать проверенные форматы к такой теме; отчёт сверяет текущую metadata, path и согласованность ссылок на source hash, но не содержание байтов. Публичный curriculum и клиенты от этого не меняются; stdout выводит только отдельные количества публичных и приватных тем. Приватная тема/связь не разрешает публикацию вопроса или непроверенного фрагмента.

## Содержательный review учебного банка

[Learning quality ledger](../content/learning-quality-reviews.json) и подписанные приватные досье фиксируют review смысла, ключа/определения, объяснения/примера, неоднозначности, повторов и источников на точном fingerprint item. Актуальные количества опубликованных вопросов и терминов выводят canonical validators; числа прежних локальных срезов не являются текущим состоянием. Primary fragments связаны с revision/fingerprint из source registry и locator; `partial`/`disputed` сохраняют причины ограничения. Discipline summaries описывают смысловые повторы; они не дают основания автоматически удалять IDs или историю.

Ledger не является publication approval, SME certification или заявлением о прочтении всех материалов корпуса. `supported` означает соответствие указанному фрагменту, а не универсальную истинность каждого клинического/методологического обобщения. Known issues сохранены и у поддержанных источником items. Подтверждённые исправления проходят отдельный publication review; старые ответы продолжают использовать snapshots. Полная сертификация legacy и устранение всех замечаний остаются F-007/008 в [плане](delivery-plan.md).

`validate_learning_reviews.py` из canonical commands [README](../README.md#быстрый-старт-и-проверки) обнаруживает пропущенные/лишние/stale items, изменившиеся sources, неполные review aspects и скрытую неопределённость. Repository regression выполняется общей pytest suite. Добавление или изменение content/source требует нового содержательного review; обновление hash без проверки источника не закрывает замечание. Raw snapshots и исследовательские заметки хранятся вне repository.

## Каталог литературы

Дисциплина чтения сохраняет прежний `topic_id` и reading identities. Необязательный `curriculum_topic_ids` связывает запись только с явно проверенными учебными темами этой дисциплины; неизвестные, повторные IDs и переход в другую дисциплину отклоняются. Связь входит в publication fingerprint: её изменение требует новой проверки/подписи. В API `curriculum_topics` содержит только стабильные ID и названия тем, без source metadata. Книги без такой связи остаются общими книгами дисциплины; фильтр темы не приписывает их всем лекциям. PWA, Mini App и Telegram используют эти же связи, личные статусы и summaries выбранного scope; выбор статуса не меняет общий счётчик темы.

Source-free библиографическая запись может хранить только `source.citation` и не иметь публичного `source_refs`, если её точная редакция подтверждена действительным publication certificate. Наличие поля certificate само по себе не освобождает от проверки подписи, fingerprint и приватного досье. Старые записи с прямым provenance остаются совместимыми; новые связи не требуют добавления Drive ID в публичный каталог. Проверка библиографической записи не подтверждает научное содержание книги.

[Литературные записи](../content/literature/) хранят отдельно библиографические связи и группировку работ. `id` — стабильный ключ записи учебного списка и существующего `user_literature_progress`; `work_id` ссылается на canonical запись той же работы. Повторные упоминания объединяются только после review автора/названия/гранулярности; совпадение названий не доказывает одинаковое произведение или издание. `module`/`topic_id` соответствуют [registry](../content/topics.json); `source` содержит ID списка, title, locator и исходную citation. Source revision/fingerprint и review находятся в едином publication ledger. Новые literature-only topics имеют `question_file: null` и не создают пустых quiz/glossary разделов.

Проверенный срез: 14 явных списков из согласованного corpus, 130 записей, 114 работ, 12 тем. Сохранены все 42 прежних IDs. Пятнадцать physiology/VND пар и Алешина counseling/family сгруппированы после ручного сравнения; отдельные годы/цитаты/источники остаются у каждой связи. Вложенные библиографии внутри всех лекций не заявлены как полностью просмотренные. Новая книга, revision или grouping требуют обычного review; frozen legacy baseline не расширяется.

`content_access: not_verified` означает, что содержание работы не использовано как учебное знание: прочитана только библиография. Отсутствующие авторы — пустой список с явной metadata warning; неизвестные год/уровень/приоритет/время — `null`, learning outcomes не выдумываются. Спорные данные остаются в citation и `metadata_warnings`. Validators проверяют структуру, ссылки и точные publication fingerprints, а не истинность содержания недоступной книги.

PWA `GET /web/literature/catalog` группирует works, но оставляет состояние каждой association отдельно. `POST /web/literature/progress` и существующий Mini App adapter используют [общий сервис](../app/literature_service.py) и проверенный actor. Пять legacy reading statuses сохраняются до решения Q-04. Никакого автоматического слияния, переноса или удаления reading rows/private notes нет; readback не раскрывает private_note. В PWA выбор учебного списка определяет, какая отметка будет изменена. При потере подтверждения записи сначала требуется readback. Личный прогресс не попадает в browser persistent cache; автоматической синхронизации открытых вкладок нет, актуальное состояние загружается при входе в раздел или по кнопке обновления.

## Release gate

Поставка следует [действующей VPS процедуре](miniapp-deployment-qa.md#действующие-правила-и-delivery-snapshot). Для schema/seed changes класс BACKWARD_COMPATIBLE_AUTOMATED: добавить поля, не удалять существующие; на время backup/migration остановить writers. Проверенный candidate image из trusted CI загружается до изменения DB; host rebuild не выполняется. SQLite backup API и isolated restore rehearsal обязательны; затем init/backfill → seed → integrity/FK и сравнение прежних user fields → snapshots/serving smoke и canonical parity → runtime start/version/health. Проверенные команды и порядок заданы [deploy.sh](../deploy.sh), [DB checks](../scripts/deployment_db.py) и [parity audit](../scripts/audit_question_bank.py).

При failed migration/post-check не продолжать поставку и не восстанавливать production автоматически. Сохранить backup/manifest, run ID и candidate SHA; сверить DB integrity/user preservation и подготовить forward-fix. Старый backend не читает snapshots, поэтому приложение не откатывается автоматически даже при совместимой additive schema. Отсутствующая/повреждённая редакция не подменяется текущим content.

Массовое обновление content — отдельный согласованный scope: content смонтирован read-only с host checkout, который обновляется до runtime restart. Размещение больших releases и проверка duration/lock window определяются до соответствующей поставки; неизменённый банк не требует искусственного content rollout.

## Unfinished sessions

После внедрения snapshots обычный seed не требует abandon активных attempts: они продолжают исходную редакцию. [abandon script](../scripts/abandon_in_progress_sessions.py) остаётся только для отдельно разрешённой операции закрытия попыток. Он не восстанавливает смысл ранее изменённой истории и не вызывается автоматически CI/CD или startup.
